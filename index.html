01

评测框架

从可核验的财报问题和运行 trace 开始，经人工错误分析与可重复测量，最后回到产品改进。每一步留下证据，避免只看最终答案猜原因。

02

Data 获取：从问题到可复核 trace

用 JojoCode 路由的 GPT‑5.6 Luna 跑受控开发题，记录用户输入、检索调用、返回财报行、模型回复与工具状态。问题设计参照真实财报助手任务形态；本批不是生产流量抽样，不能用来估算线上错误率。

事实来源SEC 真实 10‑K；保留公司、财年、报表行与原文定位。
题目口径查数、计算、澄清、材料不足；一题一会话，1–3 轮。

03

Error Analysis：先看 trace，再归纳问题

用本地审查界面支持“广度抽样 → 深度复核”：先理解字段与差异，再看代表性样本；人工自由写 notes，LLM 协助整理失效模式，最终由人确认分类。

01 / UNDERSTAND

理解数据

识别字段、轮次、工具事件和题型差异。

02 / VISUALIZE

并排呈现

内容视图、分布地图、进度视图互相定位。

03 / SAMPLE

覆盖不同样本

结合聚类代表样本与随机探索，补足覆盖盲区。

04 / REVIEW

人工审阅并记录

选中原文写 note，保留题号、轮次和上下文。

Notes 不先套分类

先记录最早能证实的错误：当时用户说了什么、Agent 做了什么、证据在哪里、正确动作应是什么，以及后续影响。这样后续归类能回到原文验证，而不是只凭标签推测。

从 notes 到失效模式：LLM 对自由文本提出归类和主题标签，合并为可执行类别；人工校正边界并保留来源定位。

04

从失效模式出发，决定是否真的需要做 eval

按“问题是否明确、规则能否稳定判断、是否需要跨版本比较”选择处理方式。Eval 是测量方法，不要求每个问题都交给 LLM。

改 Code

明确的程序、工具或证据范围缺陷。例如目标财报行被数据层排除，或计算工具不支持表达式。

改 Prompt

产品行为要求清楚，但 Agent 没按要求执行。例如逐项列来源行、保留多轮条件或不重复追问已给信息。

用 Eval

标准存在边界、同类问题反复出现，或需要比较版本。先定单项规则、补正反例，再验证改动是否改善且没有回归。

05

LLM as Judge

先把开放 notes 收敛成可观察、可举证的规则，再让 Judge 作二元判断。

① 只评一个问题证据检索失败与意图识别失败拆成两个独立 Prompt，避免一个标签混进多种错误。
② 把概念与边界写清枚举 Pass / Fail 条件、排除项与证据要求；必要时区分范围受限、不可判和运行异常。
③ 只给相关上下文输入用户轮次、trace、允许证据范围；不让 gold 或人类标签替模型作判断。
④ 输出严格受控目标标签只输出 TRUE / FALSE；内部调试可记录证据引用与信心，正式判分按单项规则执行。
当前校验状态：两项 Prompt 已分别对 80 条开发 trace 输出判定并保存为 CSV；判定由当前模型按 Prompt 逐条生成，不是独立 Judge 服务。该工作过程曾读取人工标注汇总，因此不满足盲测条件；一致率适合作为流程演示和分歧排查线索，不能证明独立裁判能力。下一轮先冻结规则，再用未参与 Prompt 调试的盲测样本复验。

07

What to do next

下一轮先校准测量，再把测量结果转成产品改动；每次只验证一个主要假设。

解释分歧

逐条比较人工与 Judge 的判定，确认是规则边界不清、上下文不足，还是 Judge 漏读证据。

检查中间步骤

如果最终答案无法定位首错，再审阅意图、检索、计算和引用等中间事件，决定是否新增单项指标。

改进并回归

选择有证据的问题修代码或 Prompt；锁定模型、工具和规则，在未参与调试的题集上做前后对照。

目标不是得到一个分数，而是得到下一项可验证的产品决策。开发集用于发现与调试；留出集用于最终比较。
